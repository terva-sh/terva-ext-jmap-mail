# Designing tools a model can actually use

Practices earned building this extension: a mail tool that a language model
drives autonomously over someone's real mailbox, with a fleet of agents filing
measured field reports against it. Every rule below cost something to learn —
a refused wave, a payload blowup, a record that turned out to be inference.
The numbers are from those reports, not from estimation.

Written for terva extensions, but nothing here is terva-specific. An MCP
server, an OpenAI function-calling schema and a terva tool are the same
problem: a JSON schema a model reads, arguments it generates, and a result
that becomes context. Where this document says "tool", read whichever you are
building.

**The single most useful framing:** the model is not a programmer reading your
API docs. It is a text generator filling in a form it has read once, whose
output you then execute against something that matters. Design for that.

## 1. Selections that must not move

The shape: the model **searches**, gets a set, **previews** an operation on it,
then **applies** it. Three calls, one set. Anything that lets the set differ
between them is a correctness bug, and everything that makes the model retype
it is a cost.

### 1.1 Give the set a handle

Return an opaque token naming the result set, and let the next call pass the
token instead of the members.

Measured on a 200-message archive batch in this extension:

| | tool traffic |
|---|---:|
| ids retyped into search → preview → apply | 10,082 B |
| named once with a handle | 4,375 B |
| handle, and the search stops returning the array too | **1,491 B** |

Two thirds of the original was the same 200 ids crossing three times, two of
those generated by the model rather than read. That is output tokens and
wall-clock, not just bytes.

The handle should be:

- **Opaque and prefixed** — see [§3](#3-a-call-should-state-its-own-mode).
- **In-memory, TTL-bounded, per-process.** Ours expire in 15 minutes and never
  touch disk. A handle that outlives the reasoning that produced it is worse
  than no handle: the model will present it after a compaction, having
  forgotten what it named. Losing one costs a re-search, which every caller
  already handles.
- **Capacity-bounded.** Ours keeps 64 of each kind.
- **Account- or scope-bound.** Refuse a handle minted for a different account
  rather than acting on it.
- **Sliceable if your mutating cap is smaller than your query cap**, with an
  offset and a `remaining` count in the result. But check first whether those
  caps still mean anything for a handle-named call — ours did not, and leaving
  them alone cost a fleet session most of its turns. See
  [§6](#6-a-limit-should-bound-the-thing-it-names).

### 1.2 Bind the applied set to the previewed set

A confirmation that names a *count* is not a confirmation. "Move 200 emails to
Archive" is satisfied by any 200 emails.

Two mechanisms, and you want both:

- **A receipt.** The dry run returns a token; the apply presents it in place of
  the ids *and* the confirmation. A receipt cannot name a different set,
  because it **is** the set. This is structural, not procedural — there is no
  argument by which a caller could hand it different members.
- **A digest in the confirmation phrase**, for callers still passing members
  explicitly. Ours reads `move 200 emails to Archive in account uc9a140ba
  [batch f7d820]`, where the digest is an order-independent fingerprint of the
  exact id set. Without it, a phrase minted by one preview confirms any other
  batch of the same size to the same destination.

A receipt should also **replay**. If the caller loses the result — timeout,
crash, compaction — re-presenting the receipt must return the original outcome
rather than acting twice. Guard the in-flight window too, so a second apply
cannot start while the first is still in the air.

For an operation you cannot undo, replay needs a third state. A receipt is
*applied* (replay the stored result), *unused* (safe to run), or **sent and
never answered** — the request reached the server and the response was lost.
For a reversible operation the third state can collapse into the second, since
repeating a move or a keyword set is a no-op. For an irreversible one it cannot:
a silent retry finds the members already gone and reports "not found", which
reads as *nothing happened* on precisely the occasion when everything did. Say
"the outcome was not recorded, go and look" instead. It is the least satisfying
answer a tool can give and the only honest one.

### 1.3 Detect drift, and report both sides of it

Even with a receipt, the world moves between preview and apply. Snapshot each
member's relevant state at preview, compare at apply, and report the
difference — **with both states**.

Reporting only the ids that drifted is a trap we shipped and had to fix: the
drift is *detected by* comparing two states, and discarding them sends the
caller back for what the comparison just established. The result now carries
`{id, was, now}`, and the remedy is readable without a second call.

Do not bind the handle to a global version token (JMAP's `queryState`, an
ETag, a table version). On a live system those advance for reasons unrelated
to the named set — the check fires constantly and tells you nothing. Fingerprint
**each member's own state** instead.

Drift is rare, so it is the one place not to economise on bytes. Never abridge
it.

### 1.4 Reversibility decides whether drift reports or refuses

Having detected drift, you still have to choose what to do about it, and the
answer is not the same for every tool.

Our recoverable operations **report and proceed**. A message that moved between
preview and apply still ends up in the archive folder the caller asked for, and
aborting a 200-message batch because one message drifted would fail far more
often than it would help.

Our one irreversible operation **refuses the whole run**. A message that has
left the place the preview saw it is a message something else acted on since,
and there is no version of "destroy it anyway" that can be walked back if that
reading was wrong. The cost of refusing is one more preview. The cost of
proceeding is unbounded.

State the asymmetry somewhere both sides can see it, or a later change will
"fix the inconsistency" in whichever direction it noticed first. Ours is written
at the top of the irreversible tool and asserted by a test that runs the same
drift through both and requires them to disagree.

The same reasoning governs the rest of the ladder. A receipt should stand in
for a typed confirmation phrase — it is strictly the stronger authorization,
since it cannot be minted without the preview actually happening, *is* the
member set rather than a fingerprint of it, records the options the preview ran
under, and cannot be presented to a different tool. Requiring both is not
double safety; it is a toll on the safer path, and the safer path is the one
you want to be cheapest. But keep the receipt's *scope* honest: if a gate held
some members back, the receipt covers what the preview showed, not what was
asked about — and if the phrase beside it still covers everything asked about,
say in the result which of the two is usable. A caller should not learn that
by being refused.

### 1.5 A handle is also how you report a subset

Once a set has a name, the name works in both directions. The obvious use is
input — the caller names a set it already has. The one that gets missed is
**output**: when a call partly fails, hand back a handle naming the part that
failed.

A list of failed ids looks like the honest answer and is nearly useless. A bare
id identifies nothing to a person, and it cannot be acted on without another
call carrying all of them back. What a caller actually wants is to *see* the
failures or to *retry* them, and both of those are "operate on this set" —
which is the thing a handle already does.

So group failures **by cause**, and give each group a handle. Not one handle for
everything: the remedy differs by cause, and at least one cause here is "there
is no remedy" — retrying a not-found group fails every time, so folding it in
with the retryable ones guarantees a wasted call on every attempt.

For this to be worth anything, a **read** tool has to accept handles too. Ours
did not, and until it did the failure handle could be retried but not inspected
— you could act blindly or not at all. That was the actual gap; the expander
tool we nearly built to "turn a handle into ids" would have solved it by
undoing the whole pattern.

The test for where else this belongs is narrow and mechanical: **does the tool
already hold a set of ids that a later call would otherwise re-derive?** Our
aggregate held each group's members during the fold and discarded them, so
"act on the top sender" cost another query per row. Our thread reader had the
complete thread and returned a capped slice of it. Both now hand back a handle.
Our counting tool never has ids at all — it asks for zero results on purpose —
so it emits none, and that is not an omission.

That last one is worth stating plainly: a handle on every result is not the
goal. A handle is worth minting when it names a set someone will act on, and
noise otherwise. Ours are also withheld at read-only access levels, where the
tools that consume them are withdrawn.

Where the emitted set is a *subset* of what the tool scanned, be careful: a
handle naming part of a group while reading as all of it is worse than no
handle, because the caller will act on it. We refuse to mint over a truncated
scan for exactly this reason. Conversely, where the emitted set is a
*superset* of what was displayed — our thread reader knows every message in
the thread but shows the newest hundred — mint it and say so in the result,
because "this acts on more than you were shown" is not something a caller
should have to infer.

One caution, and it is [§6](#6-a-limit-should-bound-the-thing-it-names) again:
the read tool's cap does **not** rise for a handle. The mutating cap bounds ids
going out, which a handle avoids. A read's cap bounds content coming back,
which a handle does nothing about. Same token, opposite conclusion — because
the caps protect different things.

### 1.6 Where this pattern applies

Anywhere a model selects then acts: files matching a glob, rows from a query,
issues from a filter, resources from a list. The tell is a tool whose arguments
repeat something a previous call just returned.

## 2. Every optional parameter needs an inert value

**The rule:** anything your code treats as "unset" must be a value the schema
permits, and that value must mean what omitting the key means.

**Why:** models routinely fill in every declared property rather than omitting
keys. This is not confusion; it is habit, and it is stable. Asking them to omit
a key does not work — we tried, and watched a model vary a placeholder value
nineteen times rather than drop the field once.

**What it cost us.** An `ids` array declared `minItems: 1` alongside two
alternative selectors. The empty array meaning "not naming ids this way" was
schema-invalid, so a padding model substituted `["placeholder"]`, then
`["dummy"]`, `["x"]`, `[""]`, `["a"]` — each read as a real selector, each call
refused as naming two. **Twenty calls, nineteen rejected, a 2,000-message
batch that moved nothing.** The validation was correct, the error message was
accurate, and the feature was unusable.

After the fix, the same model on the same work: **20 of 20 succeeded, 4,000
messages, zero rejections** — every call still padding `ids: []`. The habit
never changed. The padded value became inert.

That is the lesson worth internalising: **a better error message did not
survive contact with the model; an inert value did.**

### The checklist

- **No floor that forbids the inert value.** If `limit: 0` means "default",
  do not declare `minimum: 1`. If `ids: []` means "not this way", do not
  declare `minItems: 1`. Upper bounds are fine — they are real constraints,
  not floors.
- **Every string enum admits `""`.** Your handler already resolves `""` to a
  default or refuses it by name. Without it in the enum the model gets a schema
  violation whose text it never sees, instead of your error telling it what to
  send.
- **No parameter whose padded value is an active choice.** This is the
  dangerous one. A `hasAttachment` boolean looks harmless until you notice a
  padded `false` is a filter excluding every message that has an attachment —
  applied silently, with nothing in the result to notice it by. Ours is now a
  `"" | "yes" | "no"` string. Any tri-state that matters must be a string enum
  or an explicit sentinel, never a bare bool or a presence-checked pointer.
- **Blank array entries are padding, not errors.** `[""]` and `["  "]` should
  read exactly like `[]`.
- **Genuinely required parameters are the exception** — there is nothing for an
  inert value to mean. Still admit `""` in the enum so the refusal comes from
  your tool, naming the choices, rather than from schema validation.

### The general form

**Optionality expressed by key presence is unusable by a model that fills every
key in the schema.** Where a tool distinguishes "absent" from "zero", the
absent case needs a representable value; where it cannot, the padded value must
be inert rather than active.

## 3. A call should state its own mode

If a tool offers alternative ways to name its target, a reader should not have
to test three fields for emptiness to know which was used. That cost lands on
audit records, on recovery after an interruption, on the model reading its own
transcript back, and on your documentation.

Three shapes, in the order we would now reach for them:

1. **Make the value self-describing.** Prefix the handles: `sel_84ee6b` is a
   selection, `rcp_d18707` is a receipt. One parameter carries both, and the
   mode is read off a value the caller supplied. This *removes* a field, which
   is the only version of this change that makes your schema smaller — ours
   went from three selectors to two and the description shrank by 194
   characters.
2. **An explicit discriminator with an inert empty** — `by: "" | "ids" |
   "selection"`. Keeps existing field names, but adds surface, so it roughly
   breaks even on documentation size.
3. **Separate tools** — `move_by_selection`, `move_by_ids`. Strongest: no mode
   key exists to pad wrong. Costs a tool slot per mode per operation, which
   multiplies fast and works against a model's ability to know what it holds.

**What not to build:** nested objects per mode — `{byIds: {…}, bySelection:
{…}}`. A padding model sends `{byIds: {}, bySelection: {}}`, and three empty
objects carry strictly less information than three empty scalars. It
reintroduces [§2](#2-every-optional-parameter-needs-an-inert-value)'s trap in a
form you cannot fix with a sentinel.

## 4. Late binding is a drift hazard

A parameter that resolves to "the current one" at call time — `version: 0`
meaning head, an empty ref meaning latest, `cursor` absent meaning newest — is
a selection that can move between the model deciding and the tool acting.

It is worse when the late-bound value is also the **padding** value, because
then the dangerous call is the one a padding model makes by default.

Worked example from this extension. `email_sieve_mark_applied` records which
version of a mail-filter script is live at the provider. It took `version`,
where `0` — the padded value, and the absent value — meant "head". The sequence
that breaks:

1. The agent diffs `applied → head`, reviews v5, tells the user to paste it.
2. Anything appends v6.
3. The agent marks applied with `version: 0` → **v6** is recorded as live.
4. The store now believes v6 is at the provider. Every subsequent diff is
   computed from the wrong baseline, silently and self-consistently.

Note what makes it expensive: not that the store is wrong, but that nothing
downstream can tell. Every later diff is taken *from* the applied pointer, so a
wrong pointer produces a store that agrees with itself indefinitely.

### 4.1 Pinning is not always a handle

The obvious fix is [§1](#1-selections-that-must-not-move): have the read mint a
handle, and have the state-asserting call accept it. We built exactly that for
the destructive mail tool in the same release. We did **not** use it here, and
the reason generalizes.

A handle is a bet that the gap between preview and apply is *machine* time.
Ours are in-memory, per-process, 15-minute TTL — right when the gap is a model
deciding what to do next. The gap here is a **human pasting text into a web
UI**: unbounded, occasionally an hour, and spanning restarts. A handle would
expire in a large fraction of real uses, so the fallback path would be carrying
the correctness anyway — and a safety mechanism that is usually bypassed is one
you have not really got.

The second half of the rule was the whole fix: **require an explicit target and
refuse the padded one by name.** `version` is now mandatory in effect. It stays
`minimum: 0` and out of `required` in the schema, so a padding model's `0`
reaches the tool and gets a sentence it can act on rather than a schema
violation it never sees ([§2](#2-every-optional-parameter-needs-an-inert-value)).
The refusal names head, names the pointer it would overwrite, and says why head
is the wrong guess.

Two cheap things make explicitness workable rather than annoying:

- **The reads report what they resolved.** Both reads still late-bind `0` to
  head — that is fine, they only show you something — but each states the
  version it rendered. The number the write demands is therefore always one
  line up in the transcript, never recalled or inferred.
- **Nothing else changed.** Reads kept their defaults. Only the call that
  asserts a fact about the outside world lost its.

The trade is real and worth naming: an explicit integer is weaker than a
handle. A model *can* pass a version nobody looked at. What it cannot do any
more is pass one **without saying so** — the claim is now in the arguments, the
transcript, and the audit record, where it can be reviewed. Converting a silent
inference into a checkable assertion is often the whole available win, and it is
worth more than a stronger mechanism that expires.

**Rule of thumb:** late binding is acceptable on a read and hazardous on a
write. Ask what happens if the underlying thing changes between the call that
informed the decision and the call that acts on it. If the answer is "we act on
something nobody looked at", pin it — with a handle if the gap is machine time,
with a required argument if it is human time.

## 5. Let the caller ask for less

Every tool that returns objects should let the caller name the properties it
wants. Field projections are the single highest-leverage payload change we
made.

Measured on identical work, before and after:

| | before | after | |
|---|---:|---:|---|
| `email_search` results over a wave | 88,568 B | 8,179 B | −91% |
| a four-message placement check | 3,559 B | 1,034 B | −72% |
| all mail traffic | 128,388 B | 47,467 B | **−63%** |

Notes from getting this wrong first:

- **Be consistent across every tool that returns the same objects.** We shipped
  projections on three tools and not the fourth; an agent using it concluded no
  projection existed anywhere and reported the gap as a missing feature. State
  the convention once in whatever standing instructions you contribute, not
  only in each schema.
- **Make one tool's projection valid on its siblings.** A caller should be able
  to carry a field list across tools. Ours is a strict superset relationship.
- **A projection should narrow the request, not just the response.** Ask your
  backend for less too, and skip work the projection made unnecessary — an
  id-only projection on our search skips the per-message fetch entirely.
- **Let the caller drop the payload entirely** when a handle already names the
  set. Our search takes `returnIds: "none"`, keeping the counts, the query
  state and the handle; `"boundaries"` keeps the first and last id, which is
  enough to spot-check placement afterwards.
- **`metadata`-style flags are not projections.** Ours dropped bodies and
  returned every other property, which reads like a projection and is not.
- **Do not refuse a projection that conflicts with an older flag** — override
  it. Refusing means a padding model that filled both gets an error about a
  combination it never intended. See
  [§2](#2-every-optional-parameter-needs-an-inert-value).

### 5.1 Sometimes "less" is a different question

Projections shrink an answer. They cannot turn the wrong answer into the right
one, and the tell is the same either way: **the model is post-processing your
results.**

Watch for a loop where it fetches a batch, extracts one field, discards the
rest, and repeats. That is a tool you did not write, being emulated one round
trip at a time, and it is expensive in the worst way — the intermediate
material crosses the boundary and stays in context for the rest of the session.

Measured here. Asking "who is filling this mailbox" had no answer, because the
search tool answered exactly one question per call: *how many match this
filter*. A distribution is not a count. So the agent dumped a few hundred
message summaries, eyeballed the frequent senders, and issued a counter per
guess — **244,664 bytes, 92% of the session's mail payload**, 42 of its 62
searches, and 81% of the cost fell after those listings landed, because they
stayed resident.

Worse, it was **wrong in a way nobody could see**. Ranking senders from the
newest 200 and oldest 200 of a 3,166-message mailbox ranks them from 12% of it,
taken from both ends. A steady mid-volume sender appears in neither window, so
no counter is ever issued for it. The counts that came back were exact; the
choice of what to count was a sample, and nothing in the output said so.

Two shapes cover most of this:

- **An aggregate.** Return the distribution — ranked groups with counts — and
  never the members. Ours reads `[{key, total, unread, newest, oldest}]`.
- **A batch.** Several labeled questions answered in one call, against one
  snapshot. Rows taken one call at a time each get their own moment, so a table
  built from them does not have to add up. Ours had an agent writing itself
  Python assertions in a shell to check a mail tool's arithmetic, and it was
  right to: a survey measured 3,166 against a cleanup that closed at 3,165.

Three things make an aggregate honest:

- **State what it was computed over.** `matched` and `scanned`, and a
  `truncated` flag when they differ. Otherwise a bounded scan is the sampling
  problem again, wearing a summary's clothes.
- **Weigh the tail, do not list it.** Return the ranked head, plus how many
  groups exist and how many members fall outside it.
- **Return no content.** A group key is often third-party text — ours is a
  sender address, and we deliberately dropped the display name beside it. If
  the aggregate leaks subjects, it has reintroduced the cost it removed.

And one thing to refuse: an aggregate that can *also* return the members. The
whole value is that the intermediate material never crosses the boundary. If
the same tool can page and project, it is a search again, and the model will
use it as one.

## 6. A limit should bound the thing it names

Every cap in a tool API exists to protect something. Write down what, because
the day a new calling convention arrives, the cap will still be there and the
thing it protected may not be.

Ours capped a bulk mutation at 200 messages. The reason was argument payload:
200 opaque id strings is already a large tool call. Then handles arrived — one
short field naming a set pinned server-side — and the cap stayed, now bounding
a call that carried no ids at all. A fleet session archived 13,797 messages in
**69 applies plus 70 dry runs, 500 of 531 tool-bearing turns carrying exactly
one call, across 4h45m**. The protocol was executed perfectly. The turn count
was set by an argument-size limit the chosen convention never approached.

The test: for each cap, name the resource. If a caller can reach the same
outcome by a route that does not consume that resource, the cap does not apply
to that route.

Two things this rule does not license:

- **Removing the cap.** A bound that protects nothing under one convention
  still protects something under another — keep both, and pick by how the call
  named its target. Ours is 200 for literal ids and 2,000 for a handle.
- **Raising one cap in isolation.** Caps compose, and the smallest one governs.
  Raising the mutation cap alone bought nothing here, because a selection only
  ever held one search page and *that* cap was 500. Both had to move, and for
  the same reason: with the id array suppressed, a page enters the transcript
  as one token however large it is. Trace the whole path before claiming the
  win.

Past a certain size a call can also fail **in the middle**, which it could not
before. That is a real cost of the change, not a detail: 69 recoverable turns
traded for one unrecoverable one is a bad bargain. So chunk underneath the cap,
and when a run stops, say how far it got and hand back a handle naming what is
left — finishing is then the same two calls as any other batch, with no ids to
recover from a result that failed.

## 7. A result must be readable on its own

**The rule:** a result must be sufficient to say what happened, using
identifiers that cannot silently change meaning. Never a label where you
already hold the id, and never a bare id where you already hold the state that
made it interesting.

Both halves cost us a release.

**A label where you hold the id.** Our move result named its destination
`{id, name, role}` and its source `{"Inbox": 200}` — a display name and a
count. Display names are user-editable and repeat across parents; ids are
neither. Every ledger row the agent wrote asserted ``Inbox `P-F` → Archive
`P3V` ``, and the source half was inference carried from a baseline call twenty
batches earlier. It degrades quietly: a rename mid-run leaves a record that is
wrong and internally consistent.

**A bare id where you hold the state.** Covered in
[§1.3](#13-detect-drift-and-report-both-sides-of-it), and the same defect
appeared in our permanent-delete tool: it reported which messages the safety
gate blocked, but not where they were — on the one operation that cannot be
undone, where the remedy depends entirely on that answer.

Two useful tests when you are unsure:

- Would acting on this result require a second call to interpret it? If so, and
  you already had the answer, put it in.
- Was the ambiguous thing **supplied by the caller** or **discovered by the
  tool**? A search echoing back the mailbox id it resolved from the caller's
  own `"inbox"` is fine — the arguments and the result together establish the
  mapping. A move's *source* was discovered, and nothing else records it.

## 8. Audit by allow-list, never by redaction

If your tool touches data that belongs to someone other than the operator, and
you keep a durable record of what it did, the record's content policy is a
design decision — make it structural.

**Allow-list what may be recorded.** A redaction pass ("log the result minus
the fields we know are sensitive") fails open: the day someone adds a field it
ships to disk until a reviewer notices. An allow-list fails closed — a new
field is invisible until someone names it deliberately.

For a mail tool that means ids, counts, mailbox references, outcomes, and the
permission level in force; never subjects, senders, recipients, previews or
bodies. **And not the caller's search filter either** — a query over a corpus
is a standing description of what the corpus contains, which is the same
exposure by another route.

Other things worth getting right, all found by driving the real binary rather
than reading the code:

- **Record the permission in force**, not just the operation. A log that shows
  the destructive calls but not the access level that allowed them is missing
  the point.
- **Record permission *changes*.** They are the most security-relevant events
  and they leave no tool call behind. You need a baseline record at session
  start for the first change to be a diff against something.
- **A failed audit write must not fail the operation** — the record describes
  the work, it is not part of it. Report once, disable, and surface that state
  somewhere the operator can see.
- **Make it verifiable.** Our status tool reports whether auditing is *actually*
  recording and where — including when the extension is unconfigured or the
  provider is down, because that is exactly when someone checks.
- **State the limit.** A local append-only file owned by the process it
  describes is evidence of what your tool believes it did, not tamper-proof
  evidence. Say so rather than letting a reader assume otherwise.

## 9. Testing all of this

Most of these defects live in a JSON string, not in code, so ordinary unit
tests do not see them.

- **Parse your own schemas in a test.** Assert the invariants directly: no
  string enum without `""`, no integer floor above zero, no `minItems` on a
  selector that has an inert empty, required lists unchanged.
- **Write a "fully padded call" test per tool.** Every optional parameter set
  to its inert value, asserting the result equals the unpadded call's. This is
  the test that would have caught the wave-stopping bug.
- **Use sentinel values for content policy.** Put unmistakable strings in
  subjects, senders and filters, run real results through your audit
  projection, and grep the output. Do it against real backend results, not just
  hand-written fixtures — fixtures do not drift, code does.
- **Budget payloads in a test.** Ours runs a 200-message wave end to end
  against a hermetic server and fails if it exceeds a byte-per-message budget.
  Regressions here are invisible until someone measures a session.
- **When measuring compression or size, vary your fixture data.** 4,000
  identical records compressed to 0.5%, which proved nothing; varied ones
  compressed to 6.5%, which is the number worth quoting.
- **Read the emitted schema from the built binary** before believing a release.
  A test asserts what the code produces; only the binary tells you what the
  model receives.
- **Drive the real thing over its real protocol.** Two of our audit defects —
  a missing baseline record and a status field hidden behind a provider error —
  were invisible in tests and obvious the first time we ran the binary.

## The short version

- Name a set once; never make the model retype what you just returned.
- Bind what you apply to what you previewed, structurally.
- Snapshot per-member state; report both sides of any drift.
- Reversible operations report drift and proceed; irreversible ones refuse.
- Hand failures back as a handle per cause, not a list of ids — then a read
  tool shows them and the same tool retries them.
- Ask of every tool: does it hold ids a later call would re-derive? If so, emit
  a handle. If the emitted set is a subset of what was scanned, do not.
- A receipt replaces a confirmation phrase — charging a toll on the safer path
  buys nothing.
- Irreversible work needs a "sent, outcome unknown" state; do not retry into it.
- Every optional parameter needs a representable, inert "not this one".
- No parameter whose padded value is an active choice.
- Make the call state its own mode, preferably in a value you already return.
- Late binding is fine on a read and dangerous on a write.
- Pin with a handle when the gap is machine time, a required argument when it
  is human time.
- Let callers ask for fewer properties, consistently, on every tool.
- If the model is post-processing your results in a loop, you are missing a
  tool: return the aggregate, not the material for it.
- Counts that must reconcile belong in one call against one snapshot.
- Name what each cap protects; a route that does not consume it is not bounded
  by it. Caps compose — the smallest governs.
- A result should be actionable without a second call to interpret it.
- Allow-list what reaches a durable record; never redact.
- Test the schema, the padded call, and the built binary — not just the code.
